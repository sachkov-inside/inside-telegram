# Проверка задержки Telegram webhook

7 сентября 2026. Задача [#51](https://github.com/sachkov-inside/inside-telegram/issues/51).
Приложение осталось на source `683ce9ad9a2a7ff9e1eb519a4fd0944a917ed094`.
Изменён host-owned входной маршрут, без изменения базы, Membership или исходящего
Xray transport. Владелец явно сохранил webhook и разрешил контрольные сообщения
из своего аккаунта.

## Воспроизведение и сравнение

Время в таблице — UTC. «Ответ» означает подтверждение `sendMessage` Telegram;
наличие соответствующих сообщений дополнительно проверялось в Telegram Desktop.
Время отправки зафиксировано непосредственно перед Enter в клиенте владельца.

Во время задержек `getWebhookInfo` показывал pending update и новые
`Connection timed out`, а в очереди приложения новой команды не было. Захват
20:01:28–20:02:08 на application host не увидел входящих пакетов на TCP 443 из
опубликованных Telegram ranges; kernel drops отсутствовали. В тот же период
ошибки доставки продолжались. Этот захват локализует наблюдаемый отказ до
приложения, но не определяет конкретный узел потери пакетов.

Контрольное возвращение исходного URL/IP после такой же повторной регистрации
снова воспроизвело задержку. Поэтому улучшение нельзя объяснить одним вызовом
`setWebhook`. При возвращении relay накопленное событие поступило за доли секунды.
Каждая перечисленная команда имеет одну доставку с `attempt_count=1`.

## Включённый маршрут

`Telegram → relay:88 → application host:443 → Caddy → webhook inbox`.

Relay использует штатный `systemd-socket-proxyd`. TLS завершается на прежнем Caddy;
bot token, webhook secret и private key сертификата на relay не копируются.
Hostname и путь webhook сохранены, регистрация использует порт 88 и отдельный
`ip_address`. DNS не менялся. `allowed_updates`, `max_connections=40`, secret и
ожидающие события сохранены; `drop_pending_updates=false`. Long polling не
включался. Установка и откат описаны в [runbook](../operations/webhook-relay.md).

## Проверки

- `systemd-analyze verify` обоих units прошёл на Ubuntu/systemd 255.
- Через relay POST без secret вернул 401 за 119–224 мс, GET — 404; TLS certificate
  verification включена. TCP 88 с непредусмотренного источника блокируется.
- Порт 88 разрешён только из опубликованных Telegram webhook ranges. Relay
  работает с `DynamicUser`, без capabilities и без изменения других служб.
- SIGKILL только процесса relay в 20:09:54 вызвал автоматический restart.
  `NRestarts=1`, service active, новое соединение Telegram подтверждено захватом
  SYN/SYN-ACK/TLS, следующая команда получила один ответ.
- `pnpm check:full` под Node 24.20.0 прошёл: 275 unit и 201 integration test с
  настоящим локальным PostgreSQL. Проверки diff и discovery links прошли.

## Границы доказательства

Подтверждён обход проблемного входящего маршрута, а не точный механизм отказа
сети исходного VPS. Прямой IPv4 к Bot API тоже давал таймауты; прямой IPv6 был
быстрым в большинстве проб, но также дал один timeout. Поэтому исходящий
transport не менялся одновременно с входным.

Длительная доступность сети, перезагрузка всего relay host и автоматическое
переключение между несколькими relay не проверены. Socket включён для автозапуска;
отказ нового host остаётся отдельной эксплуатационной зависимостью. Короткая
серия успешных проверок не является гарантией отсутствия будущих сетевых сбоев.
